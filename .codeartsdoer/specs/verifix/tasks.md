## 1. M0 地基：工程骨架与领域模型（D1–D2）

### 1.1 清理抓取残留物并建立七个顶层目录
- [x] 删除根目录 `app.js`、`rc.js`、`main.js`、`dom.html`、`shell.html`；按 design 2.1.5 建立 `backend/`、`frontend/`、`mcp/`、`sandbox/`、`docs/devlog/`、`scripts/`、`deploy/` 七个顶层目录
  完成标准：仓库根目录不再存在上述五个文件，也不存在任何指向它们的 import/引用；新目录结构与 design 2.1.5 一致。

### 1.2 建立 FastAPI 后端骨架与配置加载即校验
- [x] 在 `backend/` 建立应用入口、路由装配、依赖注入与生命周期钩子；在 `backend/app/config.py` 实现 design 2.1.2 的全部配置键（`product.brand`、`branch.namespace`、`release.auto_branch`、`run.deadline_seconds`、`stage.timeout.*`、`sandbox.*`、`patch.max_lines/max_files`、`patch.strength_l0_l1_min`、`suspicion.threshold`、`circuit.fail_streak`、`blacklist.ttl_hours`、`model.provider`、`model.max_calls_per_issue`）
  完成标准：`stage.timeout` 之和 ≥ `run.deadline_seconds`、`sandbox.mem > 1g`、`run.deadline_seconds > 900`、`patch.max_lines ≠ 30` 等任一非法配置时进程拒绝启动并给出键名；`product.brand` 改动不影响 API 路径与分支前缀。
  **依赖 1.1**

### 1.3 定义领域模型与枚举
- [x] 在 `backend/app/domain/` 定义 design 2.3.2 的 12 类领域对象（`Issue`、`Alert`、`Verdict`、`Proof`、`Patch`、`AuditFinding`、`GateResult`、`Disposition`、`Run`、`Event`、`Metric`、`EvalCase`）与 `CircuitState`，全部使用 Pydantic v2 显式模型
  完成标准：状态、缺陷类别、处置级别、结论、事件类型均为枚举；`confidence`、`patch_strength` 带 `[0,1]` 约束；跨层传输不使用 `dict[str, Any]`；枚举取值与 spec 6.1 第 2/7/8 条完全一致（不含"未知"态）。

### 1.4 建立持久化层与索引
- [x] 在 `backend/app/repo/` 实现 RDS 主表与 `Event` append-only 表、`Outbox` 待执行任务表的仓储接口；按 design 2.3.2 建立 `Issue(repo, occurred_at)`、`Issue(status)`、`Issue(fingerprint)` 唯一索引、`Run(issue_id)`、`Event(run_id, seq)` 唯一、`Metric(metric_id, stage_tier, window)` 唯一索引
  完成标准：事件表数据库账号仅有 INSERT 权限，UPDATE/DELETE 被拒绝；大字段（diff、stdout、复扫输出）只落 `ref + sha256 + size`。

### 1.5 定义统一响应信封与错误码表
- [x] 在 `backend/app/api/` 实现 `{code, message, data, trace_id}` 信封与 design 2.2.1 的 `VF-1001`…`VF-9001` 错误码映射
  完成标准：错误码表以单一常量源定义（HTTP 状态 + 语义 + 触发场景），API 层不得抛出裸异常；未归一化返回 `VF-1001`、范围外返回 `VF-1002`、幂等命中返回 `VF-1003` 的可验证样例存在。

### 1.6 实现 17 条状态迁移与运行期守护
- [x] 在 `backend/app/orchestration/` 实现 design 2.1.3（1）的 T1–T18 迁移契约（含守卫与副作用），并实现 `RunDeadlineGuard`（900s 硬截止）、`ConcurrencyController`（同 Issue 互斥 + 文件级锁）、`RetryPolicy`
  完成标准：跳步迁移被拒（无 `Verdict` 请求 `REPRODUCING` 返回 `VF-2001`）；超时落"超时"终态并保留已完成证据；同一 Issue 二次并发推进只有一次生效；迁移与事件写入在同一事务内完成。

## 3. M1 审计：多源接入与归一化

### 3.1 实现 Check 适配层
- [x] 在 `backend/app/adapters/check/` 实现 `CodeArtsCheckPort`（`fetch_alerts`、`fetch_task_status`）：外部字段映射集中在一张映射表，超时 10s、退避重试 ≤3 次，失败不得等同"无告警"
  完成标准：用录制报文驱动的契约测试通过；映射表改名演练（模拟字段漂移）只需改映射表，领域模型与 Port 签名不动；拉取失败时记录"数据源不可用（Check）"并保留上一轮结果。

### 3.2 实现 Governance 适配层
- [x] 在 `backend/app/adapters/governance/` 实现 `CodeArtsGovernancePort`（`fetch_dependency_findings`），输出组件名、当前版本、受影响区间、建议修复版本
  完成标准：契约测试基于录制报文通过；空结果与"调用失败"可区分；结果可与 OSV 交叉校验。

### 3.3 实现 OSV/CNVD 依赖漏洞策略链
- [x] 在 `backend/app/adapters/vuln/` 实现 `VulnSource` 策略链：OSV 主 → CNVD 兜底；区间冲突按"取更严"裁决，保留两侧原始区间与来源标记，OSV 不可用时降置信度并标"需人工确认"
  完成标准：同一组件给出两套不同区间时，Issue 上带更严区间 + 冲突标注 + 兜底来源标记；来源标记一路传到 `Verdict` 与看板可查，中途不丢失；OSV 超时切 CNVD 的用例可复现。

### 3.4 实现四类缺陷插件与范围收敛
- [x] 在 `backend/app/domain/defects/` 实现 `DefectPlugin` 接口与四个内置插件 `C01DependencyCve`、`C02SqlInjection`、`C03CommandInjection`、`C05HardcodedSecret`（含 `matches`、`normalize`、`assertion_policy`、`template_candidates`、`is_dependency_only`）
  完成标准：四类之外（含 C02/C03 之外的注入子类）一律判"范围外"并归档、不计处置分母（`VF-1002`）；新增插件只需注册，不改编排代码。

### 3.5 实现归一化、指纹去重与多来源合并
- [x] 实现 `EventNormalizer` 与 `DedupService`：`Alert → Issue` 字段映射、定位补齐（依赖类以组件 + 版本定位）、指纹 `hash(repo, file, rule_id, 规范化代码片段)`、Redis `SETNX` + RDS 唯一索引双保险
  完成标准：Check 与 Governance 同时报告同一定位时只生成 1 条 Issue 且 `source_count = 2` 并可回溯到两条原始告警；重复触发返回既有 `issue_id` 与当前状态，不新建分支/PR/计数；未归一化告警被拒绝进入处置（`VF-1001`）。

### 3.6 实现人工提交与定时扫描两个入口
- [x] 实现 `API-05 POST /api/v1/issues`（P95 ≤2s，受理即返回、不同步等待）与 `API-02 POST /api/v1/triggers/scheduled`（`idempotency_key` 唯一，同一时间窗不重复扫描），用于 M1 阶段向靶场投喂 Issue
  完成标准：人工提交返回 `issue_id + status` 且 P95 压测 ≤2s；同一时间窗重复触发只登记一次扫描任务；接口写接入事件。

  **依赖 3.1、3.2、3.3、3.4、3.5、2.4**

## 4. M1 审计：可达性判定与定级

### 4.1 实现入口点识别
- [x] 在 `backend/app/tracing/` 实现 Python AST 入口点识别：HTTP 路由装饰器与框架注册点、定时任务、消息消费者；支持指定 commit 读取
  完成标准：靶场识别出全部已标注入口点；未识别到任何入口点时输出"入口点识别为空"事件并把整批判"可疑"，不批量归档。

### 4.2 实现调用图构建
- [x] 实现跨文件模块导入图 + 函数级有向图（邻接表），解析在进程池执行避免 GIL 阻塞
  完成标准：5 千函数规模项目建图 ≤30s（记录耗时）；跨文件调用边可被检出并给出文件与行号。

### 4.3 实现污点传播与置信度降级
- [x] 从入口点做 BFS 污点传播至 sink，命中输出完整 `taintPath`；遇动态调用、反射、装饰器链断裂时降置信度，低于 `suspicion.threshold` 判"可疑"并标注"路径可能不完整"
  完成标准：结论为"可达"时 `taintPath` 非空且首元素为受支持入口点、末元素为漏洞点；结论为"不可达"时必须写入"未找到传播路径"依据；三值结论无空值。

### 4.4 实现 Verdict 落库、定级与人工复核
- [x] 落库 `Verdict`（保留历史、最新标 `isEffective`）；按"可达性 + 严重度 + 类别"计算队列优先级；实现判定 30s 超时降可疑（`VF-2002`）与 `API-10 POST /api/v1/verdicts/{verdict_id}/review`
  完成标准：严重度相同的两条 Issue 中，可达且置信度高者排在前；人工复核产生新 Verdict 而非覆盖历史；判定超时返回"判定超时，已转人工"。

### 4.5 打通 M1 判定验收
- [x] 对靶场全部 Issue 跑判定，产出"可达 / 不可达 / 可疑"分布与人工比对表
  完成标准：≥8 条检出 Issue 均带结论与置信度；不可达且置信度达标者置"已归档"并计入无价值告警；可疑项进入人工复核队列；无可达性结论的 Issue 请求复现被驳回（`VF-2001`）。
  **依赖 3.7、4.4**

## 6. M3 修复：最小补丁与模型网关

### 6.1 实现模板补丁库
- [x] 在 `backend/app/agents/patcher/templates/` 实现四类结构性修复模板：依赖版本升级到建议修复版本、参数化查询、参数化命令调用、凭据外置到配置/密钥管理并替换字面量
  完成标准：模板产出 diff 可直接通过规模与范式校验；依赖类补丁只改依赖声明，不触碰业务代码；注入类模板不含 payload 字符串过滤写法。

### 6.2 实现 ModelGateway 与 Provider 插件
- [x] 实现 `ModelProvider` 协议与 `ModelGateway`：仅接受 `BugContext` 结构化字段（`issue_id/rule_id/defect_class/file/line/code_context/reachability_path`），输出做结构解析 + 语法校验 + 规模校验，单 Issue ≤5 次调用、单次 60s、超时重试 1 次后降级模板
  完成标准：`model.provider` 切换不改编排与提示词结构，配契约测试即可替换；超配额返回 `ModelBudgetExceeded` 并降级；自由文本输入被拒；模型不持有任何可直接执行的副作用。

### 6.3 实现规模校验、强度评分与夹带检测
- [x] 实现前置校验：≤30 行且 ≤3 文件（超限直接 L2，不裁剪，`VF-4001`）；`patch_strength ∈ [0,1]`（结构性修复高分、黑名单过滤低分，<0.60 锁 L2，`VF-4002`）；夹带检测（无关注释、格式化、重命名、依赖新增即拒）
  完成标准：三类反例（超行数、黑名单式过滤、附带格式化改动的 diff）均被判拒并给出阈值与位置；强度分与阈值被写入 `Patch` 与事件。
