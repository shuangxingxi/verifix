## 0. 一页速览

**一句话**：VeriFix 是一个跑在 CodeArts 上的安全自愈平台——CodeArts Check 发现的问题，由 AI 判定可达性、造出复现测试、生成最小补丁，再交回 CodeArts Pipeline 做门禁，最后由 CodeArts Repo 落成 PR。

**为什么这是 CodeArts 应用而不是贴牌**：它的输入、出口、判据、记录，全部由 CodeArts 提供。

| 环节 | 谁提供 | 我们做了什么 |
|---|---|---|
| 问题从哪来 | **CodeArts Check**（7000+ 规则）+ **Governance**（依赖漏洞） | 四源归一化、去重、定级 |
| 改在哪落 | **CodeArts Repo**（分支 + PR） | 自动建分支、最小 diff、PR 描述带证据 |
| 凭什么放行 | **CodeArts Pipeline**（三闸） | 把"红→绿 / 回归 / 复扫"编成流水线门禁 |
| 怎么上线 | **CodeArts Deploy**（ECS/CCE） | 灰度、失败回滚 |
| 怎么开发的 | **CodeArts 代码智能体 / IDE Online / Build** | 需求→代码→构建→修复→部署 五步留痕 |

**三个数**（初赛必须能说清）：
- 有效告警率 **20% → ≥60%**（可达性判定之后）
- 平均修复时间 **3 天 → ≤10 分钟**（单 issue 自动闭环）
- 无人干预连续自运行 **≥72 小时**

**交付物**：可访问 Demo + 完整代码（CodeArts Repo 公开仓）+ 100 条评测集 + README（组委会可复跑）+ 开发留痕归档。

## 1. 项目背景与价值

### 1.1 问题：修不完，也判不清

| 事实 | 数字 | 后果 |
|---|---|---|
| 新增 CVE 速度 | 每年 2.5 万+，且依赖链传导 | 一个底层库爆雷，下游几千个项目同时中招 |
| 静态扫描噪声 | 一个中型项目单次扫描 300–800 条告警 | 安全团队 70% 时间在判断"这条要不要管" |
| 人工修复成本 | 单个告警平均 4 小时（定位 2h + 改 1h + 验证 1h） | 300 条 = 150 人日，永远排不上优先级 |
| 修复质量 | 相当比例的修复是"黑名单式浅修复" | 换个 payload 就绕过，等于没修 |

**真正的瓶颈不是"发现"**。扫描器已经很便宜了。瓶颈是两件事：

1. **判定**——这 800 条里哪 30 条真的能被利用？
2. **验证**——改完这 3 行，怎么证明漏洞真堵上了、功能没坏？

### 1.2 现有工具断在哪

| 工具 | 能做到 | 断在哪 |
|---|---|---|
| Dependabot | 依赖版本升级 + PR | 只覆盖依赖，且不看可达性；升级撞版本冲突就停 |
| Copilot Autofix | 给出修复建议 | 建议是"文本"，没有可执行的验证；无法证明修好了 |
| Snyk Fix | 依赖 + 部分代码修复建议 | 同上；企业版昂贵，且判定逻辑不透明 |
| 传统 SAST | 规则匹配 | 只报不改；噪声大；无闭环 |

**共同缺口**：没有任何一个把"**补丁必须有证据**"变成硬约束。

### 1.3 我们的解法

```
CodeArts Check 报出 800 条
   ↓ 可达性判定（调用图 + 数据流）
剩 30 条真的能被利用                ← 有效告警率 20% → 60%+
   ↓ 造一条"现在必红"的测试
证明它确实是个洞                    ← Test-as-Proof
   ↓ 生成最小补丁（≤30 行 / ≤3 文件）
   ↓ CodeArts Pipeline 三闸
红转绿 + 全量回归 + 复扫无新增       ← 门禁，不是自评
   ↓ 分级处置
L0 自动合并 / L1 开 PR 待人审 / L2 仅报告 / L3 拒绝
```

### 1.4 价值量化（按客户算账）

| 客户 | 现状 | 用 VeriFix 之后 |
|---|---|---|
| 开源维护者 | CVE 来了手动改，一个周末没了 | 自动出 PR，人只做 review |
| 中小企业（10–100 人研发，无安全岗） | 买不起安全服务，扫描器报了没人看 | 托管式自愈，替代半个安全工程师的日常 |
| 大企业低危治理 | 安全团队 70% 时间处理低危工单 | L0 吃掉低危批量，人力转向高危 |

## 2. 创新性解读

### 2.1 创新点一：可达性判定——把"要不要修"变成可计算的问题

**做法**：从入口点（HTTP 路由、定时任务、消息消费者）出发构建调用图，对告警点做污点可达性分析，输出 `reachable: true/false` 与一条完整路径。

**为什么这是创新**：市面工具的优先级排序靠"规则严重度"，那是猜的；可达性是**从代码结构推出来的**，可复算、可解释、可被反驳。

**可量化**：同一批告警，判定前 800 条全部要人看；判定后标 `unreachable` 的 570 条直接归档，剩 230 条按可达路径排序。**有效告警率（人工确认有价值的比例）从 20% 提到 60%+。**

### 2.2 创新点二：Test-as-Proof——补丁必须自带证据

**规则**：**没有"改前红、改后绿"测试的补丁，一律拒收。** 不是建议，是硬门禁。

**为什么这是创新**：所有 AI 修代码的工具都在解决"生成对的代码"，没人解决"如何证明它是对的"。我们把举证责任压在补丁身上——补丁不自证，就不许进。

**可量化**：一次修复通过率（补丁 + 测试同时被接受的比例）；回归破坏率（补丁引入的新失败）。

### 2.3 创新点三：分级治理 + 熔断——敢让它自己跑的前提

| 级别 | 条件 | 动作 |
|---|---|---|
| L0 | 仅依赖版本号变更，且三闸全过 | 自动合并到 `release/auto` 预发分支，**永不自动并 `main`** |
| L1 | 三查 + 六条审计全过 | 开 PR，等人 review |
| L2 | 审计不过 / 补丁强度 < 0.60 | 只报告，不改代码 |
| L3 | 命中后门特征（R2–R5） | 拒绝并告警 |

> **为什么 L0 不碰 `main`**：机器人只有推 `verifix/*`、`release/*` 的权限，没有 `main` 写权限（权限基线见 `总方案.md` 14.4）。这不是保守——它让"自动"这个词可被审计：`main` 上出现的每一行，都能对应到一个人点过的 merge 按钮。L0 的自动化体现在"把补丁准备到可发布"，不体现在"跳过人的最后一道"。

**熔断**：同类缺陷连续 3 次修复失败 → 停该类处置并告警；失败指纹进黑名单，7 天内不再尝试。

**为什么这是创新**："能自动修"和"敢让它自动修"之间隔着治理设计。我们把"不敢"的原因一条条变成可执行的阈值。

### 2.4 与现有工具对比

| 能力 | Dependabot | Copilot Autofix | Snyk Fix | **VeriFix** |
|---|---|---|---|---|
| 依赖升级 | ✅ | ❌ | ✅ | ✅ |
| 代码级修复 | ❌ | ✅（建议） | ✅（建议） | ✅（PR） |
| 可达性判定 | ❌ | ❌ | ❌ | **✅** |
| 红→绿测试证明 | ❌ | ❌ | ❌ | **✅** |
| 反作弊（防改测试） | ❌ | ❌ | ❌ | **✅** |
| 分级治理 + 熔断 | ❌ | ❌ | ❌ | **✅** |
| 长时间自运行 | ⚠️ 仅依赖 | ❌ | ❌ | **✅** |

### 2.5 本轮交付范围（MVP）与演进边界

| 维度 | 本轮交付 | 演进边界（路线图） |
|---|---|---|
| 语言 | **Python 单语言** | Java / Go（v2） |
| 缺陷 | **3 类**：依赖 CVE（C01）、注入（C02 SQL / C03 命令）、硬编码凭据（C05） | 路径穿越、反序列化、弱加密、日志泄露、SSRF、配置基线、不安全随机数、竞态（v2–v3） |
| 资产 | 应用代码 + 依赖清单 + 配置文件 | IaC、容器镜像、API 契约（v2） |
| 处置 | L0 / L1 / L2 / L3 四级 | 同 |

**为什么只做 3 类，而不是 12 类。** 这 3 类恰好覆盖三种不同的验证范式：

- **依赖 CVE**：版本可判定 → 判据是"版本号在受影响区间内"（确定性）
- **注入**：数据流可追踪 → 判据是"污点从入口流到 sink"（可证明）
- **硬编码凭据**：字面量可匹配 → 判据是"高熵字符串出现在非配置位置"（可直接检出）

三种范式都跑通，说明引擎对"可验证性"的三条路径都成立；再堆 9 类只是加规则，不增加技术含量，反而摊薄 20 天工期。

**口径纪律**：`capability-matrix.html` 的 12 类是**引擎能力地图**（上限），不是交付承诺。本轮交付以本节为准；材料中任何"12 类"的表述，都必须同时出现"本轮交付 3 类"。矩阵图中标 ● 的 4 行（C01/C02/C03/C05）即 MVP 范围。

## 3. 系统设计

### 3.1 总体架构

见 `deliverables/architecture.html`（A4 横版）。赛题 1 版在右栏增加了 **CodeArts 开发链路**，并把 CodeArts 从"可选后端"提升为贯穿式基座：

```
┌──────────────────────────── 触发层 ────────────────────────────┐
│ Git Webhook(Repo) │ 定时扫描(Check) │ CVE订阅 │ 运行时告警 │ 人工 │
└───────────────────────────────┬────────────────────────────────┘
                                ↓
┌──────────────────────────── 接入层 ────────────────────────────┐
│  APIG 网关（鉴权/限流/幂等）  →  任务队列（Redis Stream）        │
└───────────────────────────────┬────────────────────────────────┘
                                ↓
┌──────────────────────────── 编排层 ────────────────────────────┐
│  Orchestrator · 状态机引擎（13 迁移 / 单 issue 超时 15min）      │
└───────────────────────────────┬────────────────────────────────┘
                                ↓
┌──────────────────────────── 智能层 ────────────────────────────┐
│ Auditor → Tracer★ → Reproducer★ → Patcher → Critic★ → Gatekeeper│
└───────────────────────────────┬────────────────────────────────┘
                                ↓
┌──────────────────────────── 工具层 ────────────────────────────┐
│ VeriFix-MCP（8 工具）＋ 沙箱执行器（断网/只读/60s/1G/非root）   │
└───────────────────────────────┬────────────────────────────────┘
                                ↓
┌──────────────────────────── 证据层 ────────────────────────────┐
│  RDS（issue/verdict/patch/metric/event）│ Redis │ OBS │ 看板    │
└────────────────────────────────────────────────────────────────┘

华为云底座：CodeArts Repo / Check / Pipeline / Build / Deploy / Governance
            ＋ MaaS ＋ ECS/CCE ＋ RDS ＋ Redis ＋ OBS ＋ APIG
```

### 3.2 六层职责

| 层 | 职责 | 不做什么 |
|---|---|---|
| 触发层 | 五种入口统一转成 issue 事件 | 不做业务判断 |
| 接入层 | 鉴权、限流、幂等去重、入队 | 不碰代码 |
| 编排层 | 状态推进、超时、重试、并发控制 | 不写 prompt |
| 智能层 | 六 Agent 各司其职，节点间显式 JSON 传参 | 不直接执行命令 |
| 工具层 | 所有副作用（读代码/跑测试/改文件/开 PR）集中在此 | 模型不能越过它 |
| 证据层 | 全链路留痕，可回放、可复算 | 不参与决策 |

**关键设计**：智能层没有任何直接副作用能力。模型只能"请求调用某个工具"，工具在沙箱里执行并把结果回传。**这条边界是后面所有安全设计的基础。**

### 3.3 一次修复的完整时序（13 步，标注 CodeArts 调用点）

| # | 步骤 | 执行者 | CodeArts 参与 |
|---|---|---|---|
| 1 | PR 合并 / 定时触发 | Repo Webhook | **Repo** |
| 2 | Check 任务执行，产出告警 | — | **Check** |
| 3 | 拉取告警 + 归一化 + 去重 | Auditor | Check API |
| 4 | 构建调用图、判定可达性 | Tracer | — |
| 5 | 造"现在必红"的测试 | Reproducer | — |
| 6 | 沙箱跑一次，确认确实红 | 沙箱 | — |
| 7 | 生成最小补丁 | Patcher | — |
| 8 | 三查 + 六条 diff 审计 | Critic | — |
| 9 | **建分支 `verifix/<issue_id>` 并推补丁** | Gatekeeper | **Repo** |
| 10 | **触发 Pipeline 三闸** | Gatekeeper | **Pipeline** |
| 11 | 读回门禁结果，判定 L0/L1/L2 | Gatekeeper | Pipeline |
| 12 | L1：开 PR 并写证据摘要；L0：合并到 `release/auto` | Gatekeeper | **Repo** |
| 13 | 写 event / patch / verdict / metric | 证据层 | OBS |

## 4. CodeArts 使用设计（本文档核心）

> 赛题 1 的硬门槛是"必须使用 CodeArts 走完开发链路"。这一章把"用在哪、怎么用、留下什么证据"写成可核对的三张表。

### 4.1 五个服务 × 五个环节

| CodeArts 服务 | 在本项目中的角色 | 不可替代性 |
|---|---|---|
| **Repo** 代码托管 | 目标仓库 + VeriFix 自身仓库；修复产物以分支/PR 形式落地 | 唯一出口 |
| **Check** 代码检查 | 问题源（7000+ 规则，支持自定义规则集） | 唯一的"发现问题"输入 |
| **Pipeline** 流水线 | 门禁执行位：三闸在这里跑，结果回写 PR | 唯一的"判据"执行者 |
| **Build** 编译构建 | 构建产物，供沙箱与部署复用 | 一次构建多次用，省时 |
| **Deploy** 部署 | 修复版本灰度上线 + 失败回滚 | 闭环的最后一环 |
| **Governance** 开源治理 | 依赖漏洞与 license 扫描（SCA 源） | CVE 类问题的来源 |
| 代码智能体 / IDE Online | 开发过程留痕（五步链路） | 赛题 1 硬性要求 |

### 4.2 开发链路五步留痕（赛题 1 硬要求）

赛题要求"需求理解 → 代码生成 → 项目构建 → 问题修复 → 部署上线"五步都有真实使用痕迹。**从 D1 开始留，不能最后补**——总决赛组委会会实跑。

| 步骤 | 用什么功能 | 产出什么 | 证据存在哪 |
|---|---|---|---|
| ① 需求理解 | 代码智能体对话：把本文档 3.1–3.3 喂进去，让它输出模块清单与接口 | 需求拆解记录、接口草案 | Repo `docs/devlog/01-requirement.md` + 对话截图 |
| ② 代码生成 | 代码智能体生成 Auditor / Tracer 骨架代码 | 带时间戳的 commit | Repo commit 历史（作者 + 时间 + diff） |
| ③ 项目构建 | Build 任务：`pytest` + `docker build` | 构建日志、镜像 digest | Build 执行记录 + 截图 |
| ④ 问题修复 | **用 VeriFix 修 VeriFix 自己**（自举） | issue → 补丁 → PR 全链路 | VeriFix 看板 run 记录 + PR 链接 |
| ⑤ 部署上线 | Deploy 发布到 ECS/CCE | 发布单、灰度记录、回滚演练 | Deploy 执行记录 + Demo 地址 |

**第 ④ 步是最有说服力的**：不需要额外的演示材料，"这个系统在给自己修 bug"本身就是证据。建议选一个真实存在的小问题（比如某个边界条件没处理），让它自己修完开 PR。

**留痕纪律**：
- 每个 commit message 带 `[step-2/codegen]` 之类前缀，便于截图取证
- 代码智能体的对话记录导出为 PDF，放 `docs/devlog/`
- 每晚把当天截图归档到 OBS，防止最后一天找不到

### 4.3 运行时四个集成点

| # | 集成点 | 方向 | 用途 | 说明 |
|---|---|---|---|---|
| I1 | **Check 开放 API** | 拉 | 获取任务的告警清单（规则 ID / 文件 / 行 / 严重度） | 定时拉取 + 任务完成回调两种模式，后者更省 |
| I2 | **Repo API** | 推 | 建分支、提交、开 PR、写 PR 描述与检查项 | PR 描述自动带"证据摘要 + run_id" |
| I3 | **Pipeline 触发 + 结果回读** | 双向 | 触发门禁流水线，轮询/回调取三闸结论 | 门禁结果必须来自 Pipeline，不能是本系统自评 |
| I4 | **Governance / 依赖扫描** | 拉 | 依赖 CVE 清单（含修复版本建议） | 与 OSV 交叉校验，取交集降误报 |

**I3 是最关键的一个**：它决定"证据可信"。评审时如果问"你的结论凭什么信"，答案是"因为门禁是 CodeArts Pipeline 跑的，日志在 CodeArts 上，不是我系统里的一张表"。

> 接口具体字段以华为云 API Explorer 中 CodeArts 对应服务的最新版本为准；本设计只约定调用语义，不锁定字段名，避免版本漂移导致返工。

### 4.4 门禁三闸（Pipeline 结构）

```yaml
# 结构示意，字段以控制台实际生成的为准
version: '1.0'
name: verifix-gate
triggers:
  - type: manual        # 由 VeriFix 通过 API 触发，不挂自动触发，避免刷流水线
stages:
  - name: proof
    jobs:
      - job: red-to-green
        steps:
          - checkout
          - shell: pytest tests/security/{{issue_id}} -q
            # 断言：该测试在补丁前必失败（VeriFix 已在沙箱记过红），此处必须绿
  - name: regression
    jobs:
      - job: full-suite
        steps:
          - shell: pytest --cov=. -q
            # 断言：0 failed，且覆盖率不低于基线 -0.5%
  - name: rescan
    jobs:
      - job: sast
        steps:
          - codearts-check:          # Check 任务
              ruleset: default
          - shell: |
              # 复扫：同规则在同一文件不得再次命中
              # 新增告警数必须为 0，否则闸门失败
```

**三闸的语义**：
1. **闸一（红转绿）**：补丁前跑一次必须红，补丁后必须绿。只有"绿"没有"红"记录 → 判无效（防止写了个永远通过的测试）。
2. **闸二（回归）**：全量测试 0 失败 + 覆盖率不下降。任一不满足 → 回滚。
3. **闸三（复扫）**：同一规则在同一文件不得再命中；新增告警数必须为 0。

任一闸失败 → 自动 `revert`，issue 转为 L2 转人工。

## 5. 数据集与处理

### 5.1 100 条怎么来（四类配比）

| 类别 | 条数 | 来源 | 用途 |
|---|---|---|---|
| 正例（真实可修） | 40 | 自建靶场 20 + 开源项目历史 CVE 20 | 测通过率 |
| 负例（不该修 / 不成立） | 30 | 误报样本、不可达告警、测试代码里的假漏洞 | 测误报率与判定准确率 |
| 边界 | 20 | 复现困难（需特定环境）、修复影响面大（跨模块） | 测降级能力 |
| 对抗 | 10 | 黑名单式"假修复"可被绕过的样本 | 测 Critic 与 patch_strength |

**必须有 30 条负例**。只有正例的评测集，任何系统都能拿高分，评委会直接质疑。

### 5.2 标注 schema

```json
{
  "id": "EVAL-0001",
  "repo": "<靶场名>",
  "issue": {"rule_id": "py/sql-injection", "file": "app/user.py", "line": 42,
            "severity": "high", "source": "codearts-check"},
  "ground_truth": {"reachable": true, "fixable": true, "expected_fix_kind": "parameterized_query",
                   "should_reject": false},
  "proof": {"test_path": "tests/security/test_eval_0001.py", "pre_patch": "fail", "post_patch": "pass"},
  "notes": "数字型注入，非字符串拼接路径"
}
```

### 5.3 负例与对抗样本怎么造

- **负例**：拿 Check 的实际误报（例如仅测试代码里的拼接）、以及标了 `unreachable` 的告警做人工复核，确认为"不该修"
- **对抗样本**：对一个洞准备两种修复——结构性修复（参数化）与黑名单修复（`replace("'","")`），标注 `expected_fix_kind`，用来检验系统是否会把后者判为通过

### 5.4 数据不泄露

评测集**不进仓库**，存 OBS；每次评测把 `sha256` 写入 `event` 表。防止有人提 PR 改标注把指标做假。

## 6. 关键代码解读

### 6.1 可达性判定（Tracer）

```python
def trace_taint(callgraph_id, entry, sink) -> dict:
    """从 entry 出发做污点传播，判断 sink 是否可达。
    返回 {reachable, path[], confidence}
    """
    g = load_callgraph(callgraph_id)          # 节点=函数, 边=调用
    tainted = {entry}                          # 入口参数视为已污染
    queue = deque([(entry, [entry])])
    while queue:
        fn, path = queue.popleft()
        for callee in g.callees(fn):
            if callee in tainted:
                continue
            if propagates_taint(fn, callee):   # 参数是否流入被调函数
                tainted.add(callee)
                if callee == sink:
                    return {"reachable": True, "path": path + [sink], "confidence": 0.9}
                queue.append((callee, path + [callee]))
    return {"reachable": False, "path": [], "confidence": 0.8}
```

**要点**：
- 复杂度 O(V+E)，中型项目（5k 函数）秒级完成
- `confidence` 用于降级：图不完整（动态调用、反射）时置信度下降，这类不直接归档，标为"可疑"交人工
- **不追求 100% 准确**，追求"能被反驳"——每条判定带路径，人一眼能看出对错

### 6.2 造红测试生成（Reproducer）

```python
# 由 Reproducer 生成，人不可手改（文件名带标记，Critic 检测到修改即 reject）
import pytest
from app.user import get_user

@pytest.mark.security
def test_iss_00a1_sqli():
    """对应 issue 00a1：app/user.py:42 SQL 注入。
    断言：恶意 payload 不得返回越权数据。
    补丁前：必须失败（证明漏洞存在）
    补丁后：必须通过（证明修复有效）
    """
    rows = get_user("1 OR 1=1")
    assert rows == [] or len(rows) <= 1, f"注入成功，返回 {len(rows)} 行"
```

**关键约束**：测试文件顶部打 `AUTOGENERATED` 标记；Critic 检测到该文件被修改 → 直接 reject（防止"改测试让自己通过"）。

### 6.3 diff 白名单审计（Critic 第四查）

```python
RULES = [
    ("R2", lambda d: not d.adds_conditional(),      "新增条件分支"),
    ("R3", lambda d: not d.adds_io_or_network(),    "新增网络/文件/环境变量访问"),
    ("R4", lambda d: not d.adds_string_const_cmp(), "新增字符串常量比较（后门特征）"),
    ("R5", lambda d: not d.touches_auth_constants(),"改动鉴权/加密常量"),
    ("R6", lambda d: d.lines <= 30 and d.files <= 3, "超出最小改动上限"),
]

def audit(diff) -> tuple[bool, str | None]:
    for rid, check, reason in RULES:
        if not check(diff):
            return False, f"{rid}: {reason}"
    return True, None
```

**为什么必须查"没多改"**：三查（红转绿/回归/反作弊）只能证明"没改坏"，证明不了"没夹带"。一个 `t != "dbg-9f3a2c"` 的条件能让测试全绿、漏洞也确实堵住了，但开了后门。

## 附录 A：CodeArts 配置要点

**Repo**
- 两个仓库：`verifix`（平台自身）、`verifix-target`（靶场）
- 分支保护：`main` 需 PR + 1 review
- 机器人账号只给"推 `verifix/*` 分支"权限

**Check**
- 规则集：默认规则集 + 自建"VeriFix 高危集"（SQLi / 命令注入 / 路径穿越 / 硬编码凭据）
- 触发：定时（每日）+ PR 触发
- 结果：通过开放 API 拉取，字段映射到 issue 表

**Pipeline**
- 三条独立流水线：`gate-red-green`、`gate-regression`、`gate-rescan`，或一条三 stage
- 只允许 API 触发，不挂 push 自动触发（防刷）
- 结果通过查询接口回读，写入 `verdict.evidence_ref`

**Build / Deploy**
- Build：`pytest` + `docker build`，产物推 Artifact
- Deploy：ECS 单机（阶段一）/ CCE（阶段二），保留上一版本用于回滚
