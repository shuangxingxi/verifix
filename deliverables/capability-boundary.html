01一句话界定

本系统是一个可验证的自动修复引擎：以「仓库 + 可执行环境」为输入，以「带证据的补丁 + 门禁结论」为输出。安全只是它的第一个插件。
它不是扫描器（只报不修），也不是代码生成器（改了但无法证明改对）。分界线是一条可执行的测试：补丁必须让一条原本变红的测试变绿，且不弄红任何其他测试。

02边界法则能力上限由「可测试性」而非模型强弱决定

可测试性  =  可自动化的边界

能判定对错   →  Detect → Reproduce → Patch → Verify → Gate   全闭环
只能人判断   →  止步 L2（仅报告 + 建议 diff）              不改代码
判不了对错   →  不纳入覆盖范围                             明确声明

03四级能力定义

级别定义人的介入典型形态
A检测 → 复现 → 修复 → 验证 → 门禁全自动无（或仅事后抽检）依赖 CVE 升级、注入类修复、配置基线对齐
B自动产出候选补丁与证据，合并权在人一次代码评审弱加密迁移、SSRF 白名单、镜像重建
C自动检测、定级、给修复建议，不改代码全人工处置竞态、契约级鉴权缺陷
✗资产承载该缺陷，但明确不覆盖—业务逻辑漏洞、0day、内存安全类

05明确不做，以及为什么边界之外一律降级为 L2 报告并转人工，不产生任何自动写入

不覆盖理由（一句话）
业务逻辑漏洞（越权、价格篡改）需要业务语义，无法自动生成「正确的业务预期」作为断言
0day / 未知漏洞无规则、无样本、无历史修复可比对，闭环缺第一环
架构级缺陷（信任边界设计错）不是几行代码能解决的，属设计决策，须人做
内存安全类（UAF、缓冲区溢出）需 sanitizer + fuzzing 长跑，属独立技术栈与工期
供应链投毒（恶意依赖包）需包信誉数据与行为沙箱，超出本引擎的证据模型
密码协议实现正确性需形式化验证，测试覆盖不到表述层

06降级与熔断任何自动动作都可撤销

最小改动约束单次补丁 ≤ 30 行、≤ 3 个文件；超出即降 L2，不自动提交
三重门禁① 变更测试由「红→绿」验证　② 全量回归零失败　③ 复扫告警数不增加；任一不满足即回滚
分级治理低危 + 有测试 + 改动 ≤ 3 行 → L0；中危或大改动 → L1；高危且方案不确定 → L2；判不了对错 → L3
熔断同类缺陷连续 3 次修复失败 → 停用该类处置并告警；失败指纹入黑名单，不重复尝试
成本闸门单 issue ≤ 5 次模型调用、≤ 0.5 元；超限转人工
全链路留痕who / what / why / evidence 四要素落库，任一自动动作可追溯、可撤销

08结论

能力地图覆盖 6 类资产 × 12 类缺陷 × 5 种触发 × 4 级处置；本轮交付 Python × 3 类，在「可用测试判定对错」的边界内实现无人干预闭环；边界之外（业务逻辑、0day、架构设计、内存安全）明确降级为人工处置，并以分级治理、三重门禁与自动回滚保证任何自动动作都可撤销。
边界清晰不是能力不足的证明，而是工程可信的前提——一个敢说清自己做不到什么的自动化系统，才敢让它自己跑。
